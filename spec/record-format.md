# Zephyr Record Format — v1 (FROZEN)

This document is the source of truth for the canonical byte layout. Two independent
implementations working only from this document must produce byte-identical records,
files, and hashes for the same input. Test vectors live in `spec/vectors/journals.json`;
an independent reference implementation lives in `test/reference.py`.

Frozen on 2026-10-06 (Phase 0). Changes to this document require a new format version.

## 1. Conventions

- All multi-byte integers are **big-endian**.
- All hashes are **SHA-256** (32 bytes).
- `GENESIS_HASH` = 32 zero bytes.
- Offsets are in bytes from the start of the named structure.
- Hex literals are lowercase.
- "MUST" / "MUST NOT" are normative.

## 2. Frozen decisions (README §11)

| Decision | Value |
| --- | --- |
| `private` flag in v1 | **Yes** (header bit 0) |
| Segment granularity | **Monthly**, by UTC month of record timestamps |
| Compression codec | **zstd** (implemented in Phase 3; v1 files are uncompressed, `version` byte reserved for it) |
| record_hash storage | **Store every** `record_hash` (revisit in Phase 3) |
| Signing key location | **Off the journal machine** where possible (Phase 5) |
| Byte/token targets | Set in Phase 3, measured against naive JSONL |
| Journal location | `~/.local/share/zephyr`, overridable via `--journal PATH` or `ZEPHYR_HOME` env var |

## 3. Record header (93 bytes)

| Offset | Size | Field | Type | Notes |
| --- | --- | --- | --- | --- |
| 0 | 1 | `version` | u8 | MUST be `1` |
| 1 | 1 | `type` | u8 | `0x01` entry, `0x02` amendment, `0x03` tombstone, `0x04` redaction, `0x05` checkpoint |
| 2 | 8 | `seq` | u64 | Global across all segments, starts at 0, strictly increasing by 1 |
| 10 | 8 | `timestamp_ms` | u64 | Milliseconds since Unix epoch, UTC |
| 18 | 2 | `tz_offset_min` | i16 | Minutes from UTC, MUST be in `[-840, 840]` |
| 20 | 1 | `flags` | u8 | Bit 0 = `private`; bits 1–7 reserved, MUST be 0 |
| 21 | 8 | `target_seq` | u64 | 0 unless the type targets a record (see §4) |
| 29 | 32 | `commitment` | bytes | `SHA-256(payload bytes)` — see §5 |
| 61 | 32 | `record_hash` | bytes | `SHA-256(header bytes [0..61) ‖ prev_record_hash)` |

The first 61 bytes (offsets 0–60) are the **header prefix**; they are the hash input
together with the previous record's `record_hash`.

`prev_record_hash` is:

- `GENESIS_HASH` for the first record of the journal (seq 0);
- the final record's `record_hash` of the previous segment, for the first record of a
  later segment;
- the immediately preceding record's `record_hash`, otherwise.

### 3.1 Type-specific constraints (MUST)

| Type | `target_seq` | `text` | `tags` |
| --- | --- | --- | --- |
| entry | 0 | non-empty | 0–255 |
| amendment | the **entry's** seq (target is always the original entry, not another amendment) | non-empty | 0–255 |
| tombstone | the entry's seq | empty | empty |
| redaction | the entry's seq | empty | empty |
| checkpoint | 0 | empty | empty |

- `target_seq` MUST be strictly less than the record's own `seq` (no forward targets).
- The target MUST exist and MUST be an `entry` record.
- An entry MUST have at most one redaction targeting it.
- A redaction applies to the target entry **and to every amendment on that entry**.

## 4. Payload (redactable region)

```
offset  size  field
0       32    salt        random bytes; 32 zero bytes for a redacted placeholder
32      2     text_len    u16, UTF-8 byte length of text
34      n     text        UTF-8
34+n    1     tag_count   u8
…       1+k   tag_i       per tag: 1-byte length k, then k UTF-8 bytes
```

- `commitment = SHA-256(all payload bytes)` — the stored payload is authenticated by
  the header's `commitment`.
- **Redacted placeholder payload**: 35 bytes of all zeros (zero salt, `text_len = 0`,
  `tag_count = 0`).
- Redaction physically replaces the target's payload bytes with the placeholder in the
  payload region only. The header (and thus the chain) is untouched.

### 4.1 Text and tag rules

- Text and tags MUST be valid UTF-8 (no surrogate codepoints).
- Text and tags MUST NOT contain C0 controls (U+0000–U+001F) or C1 controls
  (U+007F–U+009F). The LLM view is line-oriented; a newline in text would make the
  output ambiguous.
- Tag length: 1–255 bytes. Tags are non-empty, unique within a record (no duplicates),
  and compared case-sensitively. Tags are stored in the order given.
- **Normalization (frozen subset of UAX #15 NFC):** a writer MUST reject any text or
  tag containing a codepoint whose Unicode general category is `Mn`, `Mc`, or `Me`
  (combining marks; the complete merged range table is `spec/data/mark_ranges.txt`,
  generated by `test/generate_mark_ranges.py`). All other input is stored byte-for-byte
  as given and is treated as already NFC.
  - This is a strict subset of full NFC: all precomposed text passes unchanged, and
    decomposed input (e.g. `e` + combining acute) is rejected with a clear error
    instead of being silently mis-stored.
  - Documented limitation: exotic non-mark sequences that are not NFC (e.g. decomposed
    Hangul jamo) are stored as-is. Full NFC normalization is a future extension that
    does not change the byte layout.
- Maximum `text_len` is 65535 (u16). Entry and amendment text MUST be non-empty.

## 5. Hash inputs (exact)

```
commitment   = SHA-256( payload_bytes )
record_hash  = SHA-256( header_prefix[61] ‖ prev_record_hash[32] )
footer_hash  = SHA-256( footer_first_seq[8] ‖ footer_last_seq[8] ‖ footer_count[8] ‖ footer_head[32] )
```

No padding, no length prefixes beyond what is stored, no magic in the hash inputs.

## 6. Segment file layout

File name: `<YYYY>-<MM>.zph` (UTC month of the segment's first record), lexicographic
order = chronological order. One file per UTC month.

```
FileHeader (30 bytes):
offset  size  field
0       4     magic       "ZPH1" (0x5A 0x50 0x48 0x31)
4       1     version     1
5       1     flags       bit 0 = sealed (footer present); bits 1–7 reserved 0
6       8     segment_start_seq  u64
14      8     record_count       u64
22      4     header_region_len  u32  = record_count × 125
26      4     payload_region_len u32

HeaderRegion (record_count × 125 bytes), in seq order:
  0    32  record_hash (copy of the header's record_hash; enables exact tamper
           localization without re-derivation)
  32   93  header (offsets per §3)

PayloadRegion:
  per record, in seq order:
  0    4   payload_len  u32
  4    n   payload bytes (§4)

Footer (88 bytes, present iff flags bit 0 = sealed):
offset  size  field
0       8     footer_first_seq  = segment_start_seq
8       8     footer_last_seq   = seq of the last record
16      8     footer_count      = record_count
24      32    footer_head       = record_hash of the last record
56      32    footer_hash       = SHA-256 of the 56 bytes before it
```

- Total file size MUST equal `30 + 125 × record_count + payload_region_len`
  (`+ 88` when sealed).
- `record_count` MUST be ≥ 1.
- An active (unsealed) segment has no footer. The reference writer seals a segment
  when the next record would fall into a different UTC month (see §7).
- Sealed files MUST NOT be modified, except payload-region redaction (§4), which
  rewrites only the payload region (in Phase 3, only the affected compressed block).

## 7. Appends and crash safety

- Appends are atomic from the reader's view: the writer assembles the complete new
  segment bytes, writes them to an ephemeral file in the same directory, and
  atomically replaces the segment file (rename). A crash at any point leaves either
  the old complete file or the new complete file.
- The reference writer rolls the segment before appending a record whose UTC month
  differs from the active segment's month: it seals the active segment (adds footer)
  and starts the new file. The new segment's first record chains from the sealed
  segment's `footer_head`.
- **Recovery rule** (for files not produced by the reference writer, or on
  non-atomic file systems): on open, a reader MUST strictly parse the file. If the
  header region or payload region ends mid-record (a trailing incomplete record), the
  journal discards the incomplete trailing record, quarantines its bytes as
  `<name>.quarantine`, and rewrites the file with the valid prefix. Earlier records
  are never touched by recovery.
- `seq` is assigned as `previous global max seq + 1` (0 for the first record ever).
  Timestamps are supplied by the writer (default: current time); `verify` does NOT
  require timestamps to be monotonic, only `seq` to be consecutive.

## 8. `verify` algorithm

Two passes over all segment files in name order. The first failure is reported with
the segment file, `seq`, field, and a short expected/actual summary.

**Pass 1 — structure and chain** (per segment, per record, in order):

1. FileHeader: `magic` == `"ZPH1"`; `version` == 1; reserved flag bits 0;
   `header_region_len` == 125 × `record_count`; total size matches §6;
   `record_count` ≥ 1.
2. Per record: `type` is one of the five values; `version` == 1; reserved `flags`
   bits 0; `tz_offset_min` in `[-840, 840]`.
3. Chain: `SHA-256(prefix ‖ prev_record_hash)` MUST equal the stored `record_hash`.
   Failures report `record_hash mismatch at seq N`.
4. `seq` MUST equal the running expected seq (0-based, global across segments).

After all records: `prev_record_hash` becomes this segment's head; it seeds the next
segment (or is the journal head for provenance).

**Pass 2 — payloads and semantics** (in this order; the first failure wins):

5. Build the redaction set: walk records in order; each redaction record must target
   a strictly earlier record, and an entry may be targeted at most once (a second
   redaction is a failure).
6. Per record, the payload decodes cleanly (§4 rules) and:
   - if the record is redacted — the target entry, or an amendment on a redacted
     entry — its payload MUST be exactly the 35-byte all-zero placeholder;
   - otherwise: `SHA-256(payload)` MUST equal the header `commitment`.
7. Targets: every amendment/tombstone/redaction target exists, is an `entry`, and is
   strictly earlier than the record doing the targeting.
8. Sealed segments: footer fields match the region contents and `footer_hash`
   verifies.

`verify` reports redacted entries as **redacted**, not as failures.

## 9. LLM view (deterministic renderer)

Input: a journal that passed `verify`. Output (UTF-8, `\n` line endings, exactly one
trailing newline; empty journal → empty output):

```
# zephyr: seq <first>..<last> head=<head_hash_hex>
# <YYYY-MM-DD> <DDD>
HH:MM [tag1][tag2] text
HH:MM (edited) [tag1] text
HH:MM [redacted]
```

Rules (all fixed; output is byte-identical for the same input):

1. Line 1 is the provenance header: first/last global `seq` and the journal head
   (final `record_hash`), lowercase hex.
2. Entries are grouped by **local civil date**: `date = timestamp_ms + tz_offset_min`
   interpreted as an offset from UTC (not a full IANA zone). Days are sorted ascending;
   `<DDD>` is `Mon`…`Sun` (English, fixed).
3. Within a day, entries are sorted by `(timestamp_ms, seq)`.
4. The time is the entry's local `HH:MM` (24-hour, zero-padded) from its own
   `timestamp_ms` and `tz_offset_min`.
5. The effective text of an entry is the text of its **latest amendment** if any
   (amendments are ordered by `seq`), else the entry's own text. If an amendment
   provides it, the line carries the `(edited)` marker directly after the time.
6. Tag rendering: `[t1][t2]…` in stored order, one space between the tag block and the
   text; no tags → no bracket block. Tags come from the record that provides the
   effective text (the latest amendment if any, else the entry).
7. Tombstoned entries are omitted entirely (their amendments with them).
8. Redacted entries render as `HH:MM [redacted]` (time from the original entry).
9. `private` entries are never included.
10. Records that are not entry-type (amendments, tombstones, redactions, checkpoints)
    never appear as their own lines.
11. No other lines, no padding, no trailing spaces.

## 10. Checkpoints and signatures (Phase 5)

A `checkpoint` record is a normal chained record (`target_seq` 0, empty payload). The
Ed25519 signature over `(footer_head ‖ footer_count ‖ timestamp_ms)` plus the public
key is stored as a separate anchor artifact; the anchor byte format is specified in
Phase 5. This document only freezes that the type byte and the chaining are part of
v1.

## 11. Limits summary

| Item | Limit |
| --- | --- |
| `text_len` | 1–65535 bytes (entry/amendment) |
| `tag_count` | 0–255 |
| tag length | 1–255 bytes |
| `salt` | exactly 32 bytes |
| `tz_offset_min` | −840…840 |
| `seq` / `timestamp_ms` | u64 (no practical limit) |
| segment | 1+ records, one UTC month |
