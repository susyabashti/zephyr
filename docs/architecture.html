01

Architecture

Five components, two of them authoritative. The stored log is compact and canonical; everything else is derived, rebuildable, and verifiable against it. Deleting every derived artifact loses nothing.

Components, responsibilities, dependencies

Architecture components with responsibilities and dependencies
ComponentResponsibilityDepends on
CLI (zephyr) Command surface. Parses input, calls core, renders views. Capture must take ~3 seconds with no required fields. Core library
Core library Append, verify, read. Record encoding, hash chain, segments, atomic I/O, crash recovery. The only code that touches the canonical format. Canonical log (storage) · Anchors (checkpoint publishing)
Canonical log Chained records grouped into sealed segments. The single source of truth. Never modified after sealing, except payload-region redaction. Local disk (no network required to log)
Derived layer (rebuildable) LLM view renderer, search index, digests, profile, entities, MCP server. Every artifact records provenance (log range + head hash) and verifies integrity before serving. Canonical log
Anchors External, tamper-evident attestations: Ed25519-signed checkpoints in a private git repo (or second device), later OpenTimestamps proofs on sealed segment heads. Hold hashes only — never content. Core (checkpoint data) · external git / OpenTimestamps
LLM providers (external) Answer questions over exported views. Never implicit — anything sent to an LLM is an explicit user action. Verified LLM view via export --for-ai / ask

Trust & threat model

The design targets tamper-evidence, not tamper-proofing against someone who controls the machine. Each threat is mitigated at a specific phase:

Threat model with mitigations and phases
ThreatMitigationPhase
Accidental corruption / crash mid-writeAtomic append, recovery rules, verify1
Careless edit of a past entryHash chain breaks at that point1
Deliberate edit + recomputed hashesSigned checkpoints, external anchors5
Tail truncation / full chain rewriteAnchored head-hash comparison5
BackdatingOpenTimestamps on sealed segments5
Signing-key compromiseKey stored off the journal machine where possible; checkpoints still catch past rewrites5

02

Project Structure

The repo today is spec-first — only README.md (the plan) exists. The plan is deliberately language-agnostic, so the following is a draft target layout derived from its layering and phase order, not a spec requirement. Module boundaries are the important part; the directory names are a suggestion.

zephyr/
├─ spec/        # Phase 0 — the byte-level contract & test vectors (source of truth for correctness)
├─ cli/         # Command surface: log, today, search, edit, verify, export, ask, checkpoint, mcp…
├─ core/        # Canonical log: the only code that touches the format
│  ├─ records/  #   header/payload encoding, canonical bytes, hash chain
│  ├─ segments/ #   monthly segments, blocks, sealed footers, cross-segment linking
│  └─ io/       #   atomic append, crash recovery (incomplete trailing record handling)
├─ derived/     # Rebuildable views — never authoritative
│  ├─ llm/      #   deterministic LLM-view renderer (fixed rendering rules)
│  ├─ search/   #   full-text index, rebuildable from the log
│  ├─ digests/  #   weekly/monthly summaries (AI reads these first)
│  └─ profile/  #   AI-maintained living profile + extracted entities
├─ ai/          # MCP server — read-only by default, provenance header on every response
└─ anchors/     # Signed checkpoints → private git / second device; OpenTimestamps proofs

Responsibility of each major part

Module responsibilities
ModuleOwnsMust never
spec/Record header/payload layout, canonical encoding, exact hash inputs, segment/footer layout, crash-recovery rules, LLM-view rendering rules, test vectors.Drift from implemented behavior — vectors are the gate.
cli/Argument parsing, view rendering, UX (confirmations, output).Touch the log format directly; skip verify before AI-facing output.
core/Everything in the byte contract: encoding, chaining, segmentation, atomic append, recovery.Do I/O without a defined failure mode; modify sealed segments (except redaction).
derived/Search index, LLM view, digests, profile, entities — all with provenance (range + head hash).Be treated as authoritative; serve unverified data.
ai/MCP tool surface (get_entries, search, get_digest, get_profile, verify_status; add_entry off by default).Serve when the chain is invalid; leak private/redacted entries; be writable via an AI-supplied request.
anchors/Checkpoint signing/publishing, OpenTimestamps attestations, anchor comparison in verify.Store content — hashes only.

Dependency direction is one-way: cli → core → spec (via vectors); derived and ai consume the log through core’s verified reads; anchors only publish and compare hashes. Nothing derived may write back into the canonical log — the one sanctioned exception is the explicit, logged redaction mechanism.

03

Domain / Data Model

The core entity is the record: a chained, immutable header plus a committed, redactable payload. Records group into sealed segments; checkpoints and anchors externalize trust; derived artifacts reference the log by provenance rather than owning it.

Core entities

Core entities and their roles
EntityWhat it isKey properties
Record One append-only event. Types: entry, amendment, tombstone, redaction, checkpoint. seq monotonic from 0; header chained via record_hash; payload bound by commitment.
Segment Group of records (default: one per calendar month). Sealed with a footer; the next segment’s chain starts from the previous segment’s head. Footer: first/last seq, record count, segment head hash, footer hash. Never modified after sealing except payload-region redaction.
Block Compressed group of payloads within a segment (codec named in the spec; zstd recommended). Keeps headers cheap to scan and payloads compact.
Checkpoint A signed attestation of log state: head hash, record count, time (Ed25519). Published to anchors; compared during verify to catch tail truncation or full rewrites.
Anchor External storage of attestations: private git repo / second device (phase 5), OpenTimestamps on sealed segment heads (after format is stable). Hashes only — never content.
Derived artifact Search index, digests, profile, entities, LLM view output. Provenance: log range + head hash. Invalidated by new entries (staleness) and by redaction (regenerated).

Record layout

Header — chained, never modified

FieldNotes
versionformat + hash-algorithm identifier
typeentry · amendment · tombstone · redaction · checkpoint
seqmonotonic sequence, starts at 0
timestampUTC, millisecond precision
tz_offsetminutes from UTC
flagsbit field; reserved private bit; unused bits zero
target_seqfor amendment / tombstone / redaction: the affected record
commitmentSHA-256(salt ‖ payload)
record_hashSHA-256(canonical header ‖ previous record_hash)

Payload — committed, redactable

FieldNotes
saltrandom 16+ bytes, per record — a short, guessable entry can’t be recovered from the leftover commitment
textUTF-8, NFC-normalized
tagsoptional list of strings

Stored in separate regions so redaction physically removes text + salt without ever touching the chain.

The central seam: the chain depends only on headers (which include the commitment), never on the payload directly. The payload is verified against its commitment. This is what makes redaction possible without breaking the chain.

Interfaces & Contracts

Four interfaces matter: the CLI (human in), the MCP server (AI in), the canonical byte contract (implementation in), and the anchors (trust out). The byte contract is the strictest of all — two independent implementations must produce byte-identical records for the same input.

Internal boundaries

Internal boundaries and their contracts
BoundaryContract
Canonical byte contract One fully specified byte layout: fixed field order, fixed integer widths and endianness, length-prefixed strings, no optional ambiguity. The spec states exactly which bytes are hashed. Two independent implementations must produce byte-identical records and hashes for the same input — enforced by Phase 0 test vectors.
Header / payload seam The chain covers headers only (including the commitment); the payload verifies against its commitment. Redaction is the only sanctioned mutation of sealed data, and it can only touch the payload region.
CLI / core The CLI never touches the format; it calls append / verify / read. (Draft interpretation of the layering — the plan specifies layers, not function signatures.)
Canonical / derived Verify before trust: any consumer (CLI views, LLM export, MCP) checks integrity before serving data. Every derived artifact records the log range and head hash it was derived from, so stale or unsupported summaries are detectable. Redacting an entry invalidates and regenerates derived artifacts built from it.
Core / anchors Checkpoints carry head hash, count, and time, signed with Ed25519. Anchors hold hashes only — never content. verify compares against anchors when present.
Crash-safety contract Appends are atomic from the reader’s view: write the complete record, flush to durable storage, then advance the head pointer. On startup, an incomplete trailing record is detected and discarded or quarantined; it never corrupts earlier records.

External integrations & events

External integrations
IntegrationDirectionContract
Private git repository / second device Out (publish checkpoints), in (fetch for verify) Checkpoint files only — head hash, count, time, Ed25519 signature. No journal content ever leaves the machine through this path.
OpenTimestamps In (attestations of sealed segment head hashes) Added after the format is stable. A timestamp proof must verify independently of Zephyr — external, public, timestamped evidence of existence.
LLM provider Out — only via explicit export --for-ai / ask The renderer refuses to run on a log that fails verify (or clearly labels output as unverified, if the user opts in). private entries are never included. Local logging requires no network at all.
MCP clients (AI agents/IDEs) In — tool calls to zephyr mcp Tools: get_entries(from, to), search(query, limit), get_digest(period), get_profile(), verify_status(). add_entry(text) exists but is off by default and must be explicitly enabled; it cannot be enabled by an AI-supplied request. Every response carries the provenance header; an invalid chain is reported, not served silently.
Compression codec (zstd recommended) Internal, but named in the spec The codec choice is part of the byte contract — it must be standard and widely available.

LLM view contract

The LLM view is a deterministic renderer that turns verified records into the smallest reasonable text — fixed by the spec so output is byte-identical for the same input:

# 2026-09-14 Mon
09:32 fixed the auth bug, finally
14:10 [work] shipped v2 to client
16:45 (edited) call with dentist, moved to Thursday
17:20 [redacted]
  • Date header once per day; times in the entry’s local timezone.
  • Latest amendment text shown; tombstoned entries omitted; redacted entries shown as a marker (or omitted, configurable).
  • private entries are never included.
  • Output includes a one-line provenance header: the log range and head hash it was rendered from.
05

Key Flows

Six operations cover the system: capturing, trusting, correcting, removing, asking, and anchoring. Note the invariant in every AI-facing flow: verify first, then serve.

Quick log zephyr "text"
  1. NFC-normalize the text.
  2. Build the payload: random 16+ byte salt, text, optional tags.
  3. Compute commitment = SHA-256(salt ‖ payload).
  4. Build the header: seq, timestamp, tz_offset, flags, and record_hash = SHA-256(header ‖ previous hash).
  5. Atomic append: write the complete record, flush to durable storage, advance the head pointer. ~3 seconds, no required fields.
Verify zephyr verify
  1. Load segment footers; validate footer hashes and cross-segment chain links.
  2. If anchors exist, compare the head hash against the latest checkpoint / OpenTimestamps proof.
  3. Walk the chain, recomputing each record_hash.
  4. Verify each payload against its commitment.
  5. Report the exact position of any failure; report redacted records as “redacted,” not as failures.
Edit / delete edit <id> · rm <id>
  1. Resolve the target record by id to a seq.
  2. Append an amendment (new text) or tombstone with target_seq — a normal chained record.
  3. Views resolve to the latest amendment; tombstoned entries are omitted from default views.
  4. The original record remains in the log untouched — verify still passes.
Redact redact <id>
  1. Require explicit confirmation.
  2. Physically remove the target’s text and salt from the payload region — headers and commitment untouched.
  3. Append a signed redaction record noting what was removed and when; amendments quoting the redacted text are redacted too.
  4. The chain still verifies — verify reports the entry as redacted, not a failure.
  5. Invalidate and regenerate derived artifacts built from the entry. (Old backups may still hold the content; anchors never do.)
Ask zephyr ask "question"
  1. Run integrity check first — refuse (or label) if the log fails verify.
  2. Render the LLM view for the relevant range: private excluded, provenance header included.
  3. Retrieve relevant material — digests first, raw entries only when needed (saves context).
  4. Send to the LLM provider — an explicit, user-initiated network action.
  5. Return the answer to the user.
Checkpoint zephyr checkpoint
  1. Collect current state: head hash, record count, time.
  2. Sign with Ed25519 (key stored off the journal machine where possible).
  3. Publish to the private git repository or second device.
  4. After the format is stable: add OpenTimestamps attestations on sealed segment head hashes — independent, verifiable timestamps.

Architecture Decisions

The decisions that give the design its shape. “Agreed” items are frozen in the plan; the rest carry their trade-offs explicitly. Rejected alternatives are listed where the plan names them.

Architecture decisions with rationale, trade-offs, and rejected alternatives
DecisionRationaleTrade-off / rejected alternative
SHA-256 for hashing, with a hash_alg/format-version byte in every header Universally available; compatible with OpenTimestamps and most signing tools; stable for decades. Faster hashes (e.g. BLAKE3) rejected on ecosystem grounds. The version byte makes a future migration possible without ambiguity.
Ed25519 for signatures Small keys/signatures, fast verification, broad tooling support. —
Chain on headers only; payloads bound by salted commitments Makes redaction possible without breaking the chain — the single most important structural decision. Chaining the payload directly would be simpler but makes “content you later want gone” impossible. Payload integrity is commitment-bound, not chain-bound.
Salted-commitment redaction + signed redaction records Content and salt physically removed; commitment and header stay, so the log still verifies; the record of removal is itself signed and dated. The salt prevents a short, guessable entry from being recovered from the leftover commitment. Trade-off: redaction only affects the live copy — old backups may still hold the content (anchors never do, since they hold only hashes).
Append-only history — corrections are new records Any edit, deletion, or reordering is detectable; nothing is rewritten. In-place edits rejected: they destroy the evidence. Views must resolve latest-amendment; storage grows monotonically.
Anchoring in two stages: private git checkpoints (phase 5) → OpenTimestamps on sealed segment heads (after format stable) Git is simple and self-hosted — no external service. OTS adds independent, public, verifiable timestamps without trust in Zephyr itself. Rejected: publishing or storing entries on a public blockchain (only hashes are ever published) and any hosted service / multi-user sync (non-goals). Also rejected: true tamper-proofing against the machine owner — the goal is tamper-evidence backed by external anchors.
Language-agnostic spec + byte-level test vectors (Phase 0 before any implementation) Correctness is defined by spec plus vectors, not by a reference implementation; any language can implement it; two readers from the spec alone must produce identical bytes. Front-loads cost into Phase 0, and any encoding ambiguity is a phase-killer — which is why the gate requires “no field has ambiguous encoding.”
Deterministic LLM view (fixed rendering rules, byte-identical output) Token-efficient, reproducible, cross-implementation comparable; the renderer refuses to run on a failing log. A fixed format is less flexible than free-form summarization. Semantic search is deliberately deferred to Phase 8 with a pre-committed “must beat keyword search” gate — otherwise skipped.
Store every record_hash (initial design) Exact tamper localization — verify can point at the precise record. Costs space. Phase 3 measures bytes per entry against a target and, if missed, evaluates implied hashes with per-block checkpoints and re-runs the tamper tests.
Local-first; LLM access is an explicit action No network is required to log; nothing is sent to a provider without an explicit user command. AI features are opt-in per use; the MCP write tool (add_entry) is off by default and cannot be enabled by an AI-supplied request.
Segments (monthly) + block compression Bounded file growth, cheap per-segment sealing and anchoring, zstd for compact storage; headers stay cheap to scan. Monthly granularity is an assumption to confirm in Phase 0. Optional: Merkle roots per segment (phase 5) to prove a single entry without verifying the whole log.

Implementation Roadmap

Phases are strictly dependency-ordered — each builds on the previous gate passing. The plan’s rule: do not start the next phase until the gate passes.

Sequencing logic: spec first (0) → trust the local log (1) → read and correct it (2) → make it compact (3) → make it LLM-readable (4) → make rewrites externally detectable (5) → let an AI read it (6) → let an AI know you (7) → optional semantic search (8).

  1. Phase 0 — Spec and test vectors

    DeliverWritten byte-level spec (records, encoding, segment/footer layout, crash recovery, LLM-view rules) · test vectors including amendment/tombstone/redaction and deliberately corrupted cases · decisions frozen.

    GateHand-computed hash matches vectors · two readers working only from the spec produce identical bytes · no field has ambiguous encoding.

  2. Phase 1 — Append and verify

    Deliverlog + verify over a chained log (one segment) · atomic append · crash recovery.

    GateAll Phase 0 vectors pass · byte-flip / delete / reorder / forged-insert / timestamp-alter each fail verify at the exact position · kill-mid-write recovers cleanly.

  3. Phase 2 — Reading and amendments

    Delivertoday · yesterday · week · on <date> · search · edit · rm · amendment and tombstone records.

    GateGolden-output tests on a fixture journal · edits/deletes change the view while verify still passes and originals remain · timezone and midnight-boundary cases correct.

  4. Phase 3 — Segments and storage efficiency

    DeliverMonthly segments · block compression · sealed footers · payload-region separation · cross-segment chain linking.

    Gate100k-entry round trip identical · verify across segment boundaries; tampering with a sealed segment or footer detected · bytes-per-entry meets the Phase 0 target (else evaluate implied hashes + block checkpoints and re-test).

  5. Phase 4 — LLM view

    DeliverDeterministic renderer · export --for-ai · private flag honored.

    GateByte-identical output across runs and independent implementations · tokens-per-entry beats raw JSON by the Phase 0 margin · renderer refuses on a failing log · no private content in output (tested).

  6. Phase 5 — Signing, redaction, anchoring

    DeliverKey generation · Ed25519 signed checkpoints · salted-commitment redaction with signed redaction records · anchor 1: private git (or second device) · anchor 2 (after format stable): OpenTimestamps · optional per-segment Merkle roots.

    GateTail truncation and full-chain rewrite caught by anchor comparison · after redaction: content+salt gone from disk, verify reports “redacted,” commitment unmatchable against guessed content · signatures verify from spec+vectors alone · timestamp proof verifies independently of Zephyr.

  7. Phase 6 — AI access (MCP)

    DeliverRead-only MCP server with the section-8 tools · provenance header on every response.

    GateAI client answers date-specific questions correctly against a fixture journal · invalid chain flagged or refused · private and redacted entries never leak through any tool · write tool disabled by default and cannot be enabled by an AI-supplied request.

  8. Phase 7 — Derived layer

    DeliverRebuildable search index · digests · entities · profile · ask and recap commands.

    GateDelete-and-rebuild yields identical results · every digest/profile version records source range + head hash; stale ones detected after new entries or redaction · spot-check question set answered correctly using digests and entries.

  9. Phase 8 — Semantic search Optional

    DeliverEmbeddings over the LLM view, rebuildable from the log.

    GateBeats keyword search on a small labeled query set by a margin set in advance — otherwise, skip it.

Acceptance Criteria

What “done” means for each major capability — condensed from the phase gates. Each item is pass/fail, not a matter of taste.

Capture

  • A log entry is captured in one command in ~3 seconds, with no required tags or fields.
  • Killing the process mid-write leaves a log that recovers cleanly (incomplete trailing record discarded or quarantined).

Integrity & verification

  • Flipping a byte, deleting a record, reordering, inserting a forged record, and altering a timestamp each make verify fail and report the exact position.
  • verify works across segment boundaries; tampering with a sealed segment or its footer is detected.
  • Two implementations working only from the spec produce byte-identical records and hashes for the same input.

Editing without rewriting

  • edit and rm change what views show while verify still passes and the original records remain present.
  • Timezone and date-boundary cases (entries near midnight, timezone changes) produce correct “on date X” results.

Storage efficiency

  • 100k synthetic entries round-trip: write, read back, identical.
  • Measured bytes per entry meets the Phase 0 target (baseline: naive JSONL). If missed, the implied-hash + block-checkpoint fallback is evaluated and the tamper tests re-run.

LLM view

  • Same input produces byte-identical output across runs and across independent implementations (vectors).
  • Token count per entry beats raw JSON by the margin set in Phase 0.
  • The renderer refuses to run on a failing log; no private content ever appears in output (tested).

Tamper-evidence & redaction

  • Truncating the tail, or fully rewriting the log with a new valid chain, is caught by comparison with an anchor.
  • After redaction: content and salt are gone from disk, verify passes and reports “redacted,” and the commitment cannot be matched against guessed content.
  • Signature verification works from the spec and vectors alone; a timestamp proof verifies independently of Zephyr.

AI access (MCP)

  • Against a fixture journal with known facts, an AI client correctly answers date-specific questions (“what did I do on date X?”).
  • The server flags or refuses when the chain is invalid; private and redacted entries never leak through any tool.
  • The write tool is disabled by default and cannot be enabled by an AI-supplied request.

Derived layer

  • Deleting the index and rebuilding yields identical results.
  • Every digest and profile version records its source range and head hash; a stale one is detected after new entries or redaction.
  • Spot-check set: a handful of questions with known correct answers are answered correctly using digests and entries.

Definition of done — v1

Phases 0–6 passed: you can log in one command, run verify and trust the result, hold external anchors that expose any rewrite, redact content when needed, and ask an AI “what did I do on date X?” through a read-only server that checks integrity first. Phases 7–8 add the “get to know me” intelligence.

Open Questions

Items the plan explicitly leaves to be finalized, plus ambiguities noticed while drafting (marked inferred — worth confirming, not yet stated in the plan).

  • Phase 0

    private flag in v1?

    Whether to include the reserved private header bit in the v1 format. Recommended: yes — adding a header field later means a format migration.

  • Phase 0

    Segment granularity

    Monthly segments are assumed. The byte contract (footer layout, cross-segment linking, OTS unit) depends on the choice, so it must be frozen in the spec.

  • Phase 0

    Compression codec

    zstd is recommended. The codec is named in the byte spec, so the decision is permanent for v1. Recommended: zstd (widely available, strong ratio).

  • Phase 0 → 3

    Stored vs. implied record_hashes

    The initial design stores every record_hash for exact tamper localization. Phase 3 measures the cost and may switch to implied hashes with per-block checkpoints if the bytes-per-entry target isn’t met.

  • Phase 5

    Where the signing key lives

    Off the journal machine is stronger (key compromise can’t rewrite + re-sign history in one stroke). Needs a concrete mechanism: separate device? hardware key? offline signing flow?

  • Phase 0

    Numeric targets: bytes per entry, tokens per entry

    Both gates in Phases 3–4 reference targets “set in Phase 0.” Baseline for bytes: naive JSONL. Baseline for tokens: raw JSON. The numbers need to be chosen before those gates can be judged.

  • Inferred

    How redacted entries render in the LLM view

    The spec says redacted entries are “shown as a marker (or omitted, configurable)” — the configuration surface (flag? config file? per-range option?) is not defined.

  • Inferred

    zephyr ask — which LLM, and how is it configured?

    The plan is provider-agnostic, but says nothing about how the user selects/configures a provider (env var? config file? CLI flag?) or how keys are stored.

  • Inferred

    How MCP add_entry is enabled

    “Off by default and must be explicitly enabled” + “cannot be enabled by an AI-supplied request” implies a user-only mechanism — but config file, CLI flag, or environment variable is unspecified.

  • Inferred

    What makes the format “stable” enough for OpenTimestamps?

    Anchor 2 is gated on “after the format is stable,” but no milestone declares stability. Suggest: after Phase 3 passes and segment/footer bytes are frozen in the spec.
